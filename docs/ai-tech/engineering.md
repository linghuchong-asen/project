# 工程化踩坑与质量属性

本章收录开发过程中遇到的真实问题与解法。每个难点都按"问题→思路→收益"的结构组织——这是面试中最有说服力的部分，因为它证明了方案不是纸上谈兵，而是在真实约束下打磨出来的。

## 11.1 已解决的关键难点总览

| 难点 | 根因 | 解法 |
|------|------|------|
| 输出数据可靠性 | 模型输出不确定，前端渲染需合法 X6 JSON | 中间数据层：模型只返回语义结构，坐标交 @antv/layout，样式/ports 交节点类型映射表，确定性代码兜底 |
| Modify 场景 | 不能动用户已调好的节点；需区分已有/新增/删除、防误删、算新坐标 | 模型返回数据与当前数据 diff 定类型；边校验防误删；新增节点用碰撞检测计算布局 |
| Token 爆炸 | 长上下文直接灌入 | 中间表示把上下文从 ~2000 降到 ~600-700 token；分块 + 预算管控 |
| 模型输出不稳定 | 格式/结构易错 | Zod Schema + 中间层 + 三层反思校验 |
| 多轮话题漂移 | 长期对话跑题 | 基于 embedding 相似度的 topic shift 检测 |
| SSE 连接泄露 | 前端断开后端仍跑模型 | AbortController 显式管理连接生命周期 |
| 记忆生命周期 | 写入/压缩/召回/遗忘无管理 | 分层 + 衰减遗忘 + 评估后召回 |

## 11.2 踩坑详解

### Token 消耗爆炸

**问题**：早期让模型直接输出 X6 完整 JSON，坐标、样式、ports 占了大半 Token。单次生成调用消耗约 2000 Token，其中超过 60% 是在传坐标和样式信息——这些对语义毫无贡献。

**思路**：引入中间表示层，模型只输出流程语义结构（节点 ID、标签、类型、连接关系），坐标和样式全部交给确定性代码计算，Token 降到原来的 1/3。modify 场景注入当前画布的完整 FlowDraft（带 ID），让模型复用已有 ID 做增量 diff——若降级成"结构摘要"则模型看不到 ID，按节点 ID 匹配的前提就不成立。

**收益**：单次调用 Token 从 ~2000 降到 ~600-700，降幅约 2/3。同时模型出错概率显著降低——输出结构越简单，格式出错的概率越小。

### 模型输出格式不稳定

**问题**：Qwen 偶尔会在 JSON 前面加一段解释文字（"好的，以下是流程图数据："），或者输出的 JSON 里节点 ID 重复。靠 System Prompt 约束不够——模型是概率性的，再强的 Prompt 也无法 100% 保证格式正确。

**思路**：两层防御。第一层，用 Zod Schema 校验模型输出，不合法直接拒绝并触发反思重试。第二层（更根本的），引入中间表示层——语义结构比 X6 JSON 简单得多（只有 ID、标签、类型、连接），模型出错的搜索空间本身就小了很多。

**收益**：格式合规率从约 85% 提升到接近 100%。中间表示层不仅解决了格式问题，还顺带解决了 Token 浪费和布局不稳定的问题——一个设计决策解决了三个问题。

### 多轮对话话题漂移

**问题**：用户聊着聊着突然跳到另一个话题，历史记忆污染当前上下文。比如用户之前在聊"请假流程"，突然说"帮我画一个电商下单流程"，系统还在用请假流程的记忆做上下文，导致生成的流程图混乱。

**思路**：话题切换检测——计算当前输入与最近几轮对话的 Embedding 相似度，低于阈值时判定为话题切换，触发新摘要生成，不把旧话题的记忆带进来。检测用代码（embedding 计算 + 阈值判断），不需要模型参与。

**收益**：话题切换场景下的生成质量显著提升，避免了"记忆越多越帮倒忙"的问题。这也是"确定性优先"原则的体现——用代码做判断，模型只负责生成新摘要。

### SSE 连接泄漏

**问题**：前端关闭对话窗口或刷新页面时，后端的 SSE Observable 不会自动 complete，LangGraph 仍在继续跑模型调用，白白消耗 Token 和计算资源。

**思路**：加 AbortController，前端断开时显式 abort 后端的 SSE 流。但这个问题暴露了一个更深层的设计缺陷——SSE 和 LangGraph 的长期运行工作流配合时，需要显式处理连接生命周期，不能依赖框架的自动清理。

**收益**：消除了资源泄漏问题。同时推动了架构层面的改进——LangGraph 的每个节点在执行前检查 abort signal，一旦收到中断信号立即停止，不会继续调用模型。

### Modify 场景的 diff 与防误删

**问题**：用户说"把审批节点改成两个"，系统需要在已有画布上做增量修改。难点是：① 不能动用户已经手动调整过位置的节点；② 要区分"已有节点修改"和"新增节点"；③ 模型可能返回错误的删除指令，导致用户数据丢失。

**思路**：模型返回的数据与当前画布数据做 diff，按节点 ID 匹配确定类型（已有/新增/删除）。对删除操作加边校验——如果模型要删除的节点在当前画布中不存在，或者删除后会导致图结构不连通，则拒绝执行并提示用户确认。新增节点的坐标用碰撞检测算法计算，避免与已有节点重叠。

**收益**：实现了安全的增量修改，用户手动调整的布局不会被覆盖，误删风险被校验层兜住。这是"确定性优先"原则的又一个体现——模型的修改指令必须经过确定性校验才能执行。

### JWT 认证踩坑

**问题**：两个坑导致鉴权一直不生效，排查花了大量时间。

**思路**：

1. `class JwtStrategy extends PassportStrategy(Strategy, 'jwt')` 中的 Strategy 应该导入自 `passport-jwt` 而不是 `passport-local`。错误导入导致请求一直走 local 策略，JWT token 永远不被解析。排查方式：断点进到 node_modules 中查找 Strategy 的来源。
2. `@UseGuards(JwtAuthGuard)` 中 `JwtAuthGuard` 是一个独立的守卫类，不能和 `AuthGuard('jwt')` 混用。一开始以为两种方式等价，实际上 `JwtAuthGuard` 封装了自定义逻辑（如 Redis 校验），用 `AuthGuard('jwt')` 会跳过这些逻辑。

**收益**：鉴权链路跑通。踩坑经验沉淀为团队文档，后续新成员不再重复踩同样的坑。

### Redis 版本兼容

**问题**：安装的 redis 是 v5 版本，但代码按 v4 的方式使用 `cache-manager-redis-store`，导致缓存初始化失败。

**思路**：v5 版本需要使用 `cache-manager-redis-yet` 包来导入 `redisStore`。排查过程：看 npm 包的 README 和 changelog，确认版本对应的 API 变化。

**收益**：修复后缓存正常工作。教训：依赖升级时必须看 changelog，不能假设小版本升级 API 不变。

### 依赖升级的风险

**问题**：第一版是 22 年做的，24 年改的时候升级了 antv-x6、react-query 等依赖到最新版，结果出现变量未导出、方法传参类型变了，导致 vite 打包都通过不了。包之间还有相互依赖，升了一个就要升另一个，连锁反应。

**思路**：旧项目维护时，业务能满足就不要升级依赖。如果必须升级，先在独立分支做，跑全量测试，对比升级前后的行为差异。

**收益**：避免了不必要的升级风险。这也是为什么很多团队在 antd 等基础库上再封装一层——升级完底层库后可以用中间层做适配和测试，隔离变化对业务代码的影响。

### NestJS 序列化反序列化

**问题**：通过单独的逻辑定义传参和返回数据的结构，使前后端内部逻辑进一步解耦。但对 class-transformer 使用不熟练，在 `@Expose` 装饰器、`plainToInstance()`、`instanceToPlain()` 方法上绕了挺长时间——字段名不一致、嵌套对象转换不符合预期。

**思路**：系统学习 class-transformer 的装饰器体系，明确 `@Expose` 控制序列化时暴露哪些字段、`plainToInstance` 把普通对象转为类实例（触发验证和装饰器逻辑）、`instanceToPlain` 反过来。关键是理解"什么时候需要实例、什么时候需要纯对象"。

**收益**：前后端数据结构解耦，接口返回的结构可以独立于内部数据模型演进。

## 11.3 质量属性

| 属性 | 实现方式 |
|------|---------|
| 可靠性 | 确定性优先、结构化错误、优雅降级、三层反思闭环 |
| 可用性 | SSE 流式、AbortController 防泄露、复杂度路由降本提速 |
| 可观测 | Langfuse trace + 日志，打开黑盒，支撑评估与发版闸门 |
| 可扩展 | Skill 配置化动态注册、中间层解耦渲染引擎（可切思维导图等） |
| 安全性 | Token 配额、Prompt 注入防御、工具白名单、数据隔离（详见[安全](./security.md)） |

## 11.4 思考问题记录

1. **Token 消耗问题**：如果应用支持通过 AI 对话框修改当前流程图，那么要把当前图的 JSON 提供给大模型，这确实是个浪费 token 的方案，但如果不传 JSON 又没有办法支持通过 AI 对话修改流程图 → 解决方案：传完整 FlowDraft 语义结构（已砍坐标/样式/ports，比 X6 JSON 省 2/3），而非 X6 完整 JSON
2. **历史会话如何存如何取** → 记忆管理分层架构
3. **是否可以将结束对话作为存入的触发条件** → 是，Session-based Update
4. **是否有必要使用 LangGraph 的 persistence 架构** → 是，需要 Checkpointer 做短期记忆、Store 做长期记忆
5. **系统提示词和向量数据库的角色** → 大量文本存向量库，系统提示词做背景介绍
